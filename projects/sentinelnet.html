Overview

Security alerts need a reliable path from ingestion to triage.

SentinelNet was a team project built around Wazuh security telemetry. The system buffers incoming alerts, processes them in Python, stores normalized records in DynamoDB, and makes them available to an authorized API and dashboard.

My contributions focused on the Wazuh-to-SQS-to-Lambda ingestion path, Python Lambda processing, DynamoDB persistence, AWS CDK, and backend security integration.

System architecture

Wazuh → SQS → Lambda → DynamoDB → API

Wazuh produces security alerts. Amazon SQS buffers the messages, a Python Lambda function transforms them, and DynamoDB stores the normalized records. An API exposes authorized access for the triage dashboard.

Why SQS

The queue separates alert production from processing.

Wazuh can continue sending alerts while Lambda processes messages at its own rate. That separation helps absorb bursts and gives failed messages a retry path without requiring the producer to understand downstream storage.

The tradeoff is eventual consistency and more queue behavior to monitor, but that was a better fit than tightly coupling alert production to a synchronous backend request.

Backend processing

Normalize each alert before persistence.

The Python Lambda layer consumes SQS messages, transforms the incoming Wazuh fields into a consistent application shape, and writes the record to DynamoDB. Keeping that normalization in one backend step prevents API and dashboard code from repeatedly interpreting raw alert formats.

I worked on this processing path and the DynamoDB persistence layer, including the boundaries between message ingestion, transformation, storage, and downstream access.

Infrastructure as code

AWS CDK keeps backend resources and policies in versioned Python.

I contributed infrastructure definitions for the queue, Lambda processing, persistence, encryption, identity, and authorization. CDK made resource relationships reviewable and reduced the amount of manual console configuration needed to reproduce an environment.

It also made backend changes easier to discuss as code: a queue policy, Lambda permission, or database relationship could be reviewed alongside the application logic that depended on it.

Security model

Encryption, identity, and authorization are part of the backend.

The system uses KMS-backed encryption, Cognito identity, group-based role access, and API authorization. My backend work included integrating these controls with the ingestion and persistence infrastructure.

Permissions were organized around the components that needed them: processing functions, storage access, API operations, and analyst roles. That kept security configuration connected to the resources it protected.

Testing

We tested the full event path with hundreds of alerts.

End-to-end tests exercised alert production, SQS delivery, Lambda transformation, DynamoDB writes, and downstream access. Testing the whole path helped expose integration problems that were not visible when each resource was checked in isolation.

Queue retries, malformed records, duplicate delivery, schema consistency, and access permissions were important parts of the test plan for an event-driven security system.

Results

A working, reviewable path from Wazuh to the triage interface

  • The team validated the pipeline with hundreds of security alerts.
  • Alert production, processing, persistence, and dashboard access are separated into clear components.
  • Core AWS resources and backend security controls are defined through CDK.
  • The public repository shows the team implementation and infrastructure.
